# 2026-09-17

## Concept art: CKAN 2.0 UI mock

Created `Concept Art/index.html` — a single self-contained HTML concept for what the
GUI could look like with no WinForms/legacy constraints. **No other repo files were
touched** (explicit user constraint: "just make the html, do not edit any files").

What it shows, and the design decisions worth remembering:

- Palette values are lifted verbatim from `GUI/Discover/SoftTheme.cs` (dark + light),
  so the concept stays honest to the shipped soft theme.
- Structure: title bar (no menu bar) → left rail (Discover / Library / Updates /
  Queue / Collections / Settings) → browse surface → right inspector → change-set
  status bar. The 12,000-row grid is replaced by intent-shaped shelves.
- The **change set is the app's primary object**: staged work is always on screen,
  named, cancellable, applied as one animated transaction with per-mod stages.
- Collections (named setups) are a proposed new concept — not in the codebase.
- Cover art is generated procedurally from an FNV-1a hash of the identifier, exactly
  as `ModArtGenerator.cs` does it (never a language hash).
- Mod names / authors / download counts are real catalogue entries.

Later revisions the user asked for:
- Removed the green status dot from the title-bar instance chip (kept the text).
- Renamed the `My mods` filter pill to `Installed`.
- Added a 4-way view switcher (Large gallery / Gallery / Compact / List) driving the
  shelves, the "See all" gallery and the Library. Choosing List on Discover flattens
  the whole catalogue into rows; shelves return at any gallery size. Bound to `V`.
- Stripped almost all subtitle/helper prose — headlines only, terse data lines.

## Verification method (reusable)

No GUI test harness exists for this repo, but a static HTML mock can be verified:

1. Extract the inline script and `node --check` it for syntax.
2. `jsdom` (installed in the managed node workspace) with
   `runScripts:"dangerously", pretendToBeVisual:true` — drive real clicks/input
   events and assert on the DOM. Catches every runtime error in render paths.
3. Headless Edge for visual checks:
   `msedge.exe --headless=new --screenshot=<win path> --window-size=W,H
   --virtual-time-budget=3000 --user-data-dir=<temp> "file:///..."`
   Use Windows-style paths for `--screenshot`/`--user-data-dir` or nothing is written.
   `--virtual-time-budget` is required or the screenshot lands before JS renders.

## Gotcha: parallel Edit calls

Batching multiple `Edit` calls against the **same** file in one message silently
dropped some of them (reported success, no change on disk). Always edit one file
sequentially, and grep to confirm each edit landed before moving on.

## Transfer sheet fix (apply / cancel / retry)

User wanted: deletion to read "deleting" not "nothing to download"; Retry hidden
unless an error occurs; Cancel shown only while a transfer is in flight and gone
once it finishes.

- Root bug: `.btn{display:inline-flex}` overrode the UA `[hidden]` rule, so the
  `hidden` attribute on Retry/Cancel/Pause never actually hid them — always visible.
  Fixed with `.btn[hidden]{display:none}`. (Generic CSS lesson: any author `display`
  on an element defeats `[hidden]`; always add `.x[hidden]{display:none}.)
- "deleting" wording: `paintTransfer` sub is now `allRemove ? "deleting from
  GameData" : (downloadMB ? size : "nothing to download")`; `xferRender` bytes line
  uses `removing ? "deleting" : "nothing to download"`. Cached (no download, not
  removal) still correctly says "nothing to download".
- Verified with jsdom (`ckan_xfer.js`): removal → sub "deleting", cancel visible /
  retry hidden mid-transfer, both hidden after finish; cached → "nothing to download";
  failure → retry visible, cancel hidden. 0 JS errors.
